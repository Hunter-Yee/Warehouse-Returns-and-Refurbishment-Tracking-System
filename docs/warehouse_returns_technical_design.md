# Warehouse Returns and Refurbishment Tracking System

Technical Design Document - midterm design 1.0  
Rajdeep Villuri and Hunter Yee | Database Systems Implementations | October 24, 2026

**Baseline:** [FRD 2.1](warehouse_returns_frd_simplified_v2_1.md) and [ERD 2.1](warehouse_returns_erd_v2_1.md). This document specifies the implementation; it does not claim that a database has been built or tested. The FRD and ERD now use the selected local composite work-order key described in Section 3. SQL implementation follows this design.

## 1. Implementation scope and technology

Implement the established returned-unit lifecycle, five reports, five business roles, audit history and transaction demonstrations. Keep one warehouse, one unit per return line, USD amounts, one lifetime claim per item and total repair labor/parts costs. No repair-parts inventory, payment processing, reopening or general correction subsystem is added.

The proposed target is **MySQL 8.4 with InnoDB**, using MySQL Workbench or the mysql command-line client for the midterm. Record the actual server version when building; do not assume the installed version. InnoDB supplies transactional storage and foreign keys. MySQL is the course's specified DBMS; the version is a proposed implementation target, not a claim that it is installed. Use utf8mb4, explicit constraints and strict SQL mode. Keep all participating tables on InnoDB.

Use `ReturnHeader` and `AppUser` as SQL names for the ERD's `Return` and `User`. All other entity names stay the same. This avoids quoting ambiguous names throughout the implementation; it does not add tables. Use the ERD attribute dictionary for column names and type lengths, including the composite work-order key below.

IDs use unsigned integer types; event times use DATETIME(6); monetary inputs use DECIMAL(12,2); booleans accept only 0 or 1. `NULL` means no applicable or not-yet-known value. It differs from a known zero amount. Ordinary surrogate IDs are generated by MySQL; work orders instead use a positive local number allocated within each item as described in Section 3.

For the fictional demonstration, propose UTC for stored event timestamps and reporting boundaries. Each connection explicitly sets its time zone. This is a project convention to approve before seeding, not an inference about a real warehouse's location. Reports take inclusive start and exclusive end timestamps. CalendarMonth is the first day of the reporting month.

## 2. Architecture and data flow

The midterm client is a SQL client connected to one MySQL database. Staff connect through individual limited database accounts. Stored procedures form the controlled write boundary; procedures and reporting views read/write the normalized business tables. Database triggers update item location and append the corresponding item audit history. There is no independently deployed service or production website in this milestone.

A later application can call the same procedures through a small service layer. Do not add microservices solely to demonstrate the database. Earlier architecture/API/wireframe milestones still need the required diagram source/export if the instructor expects them; the text here is an architecture specification, not a substitute for those diagram artifacts.

| Flow | Input | Processing and output |
| --- | --- | --- |
| Intake | External reference, products, reasons, serials and location | Validate receiving identity and active references; create header and all unit lines atomically; return item keys. |
| Inspection/repair | Item key, result/grade, optional repair reference and work/cost details | Validate actor, current state and repair timing; append inspection or update assigned work; transition item; append audit. |
| Disposition/movement | Item key, expected source, destination, path/value | Validate Manager approval and movement eligibility; trigger updates current location; commit final state/time and audit together. |
| Claim | Item key, claim amount/status or received settlement | Manager-only change; reject a second lifetime claim; allow settlement of an existing claim after item completion. |
| Reporting | Item key, search filters or period | Execute authorized reads; return RQ-01 through RQ-05; financial payloads restricted to Managers. |

Conceptual future screens are Intake, Item History/Inspection, Assigned Work, Manager Decision/Claims, Reports and Administration. Each screen calls the appropriate controlled operation; hiding a button is not an authorization control. Actual wireframes and HTTP endpoints remain later design artifacts.

## 3. Relational design and normalization

### 3.1 Normalization rules used

1NF: store one value per business field; no repeated inspection groups or comma-separated role lists. Audit JSON contains a single historical document per audit field, not a replacement for operational relations.

2NF: every non-key business fact must depend on an entire candidate key. For example, monthly UnitsSold depends on both product and month; an item's serial and location depend on the return plus line number. Vendor details depend on VendorID and therefore live in Vendor, not on each returned line.

3NF: for every nontrivial functional dependency X -> A, X must be a superkey or A a prime attribute. Check alternate candidate keys too. Separating lookups and avoiding stored report totals helps, but does not by itself prove 3NF.

### 3.2 Keys and dependencies in the current baseline

The notation K -> other columns means the identified key determines the remaining attributes in that row under the documented business assumptions. It does not mean the foreign-key value determines the child record.

| Relation | Candidate keys / main dependencies | Review |
| --- | --- | --- |
| Vendor | VendorID -> vendor/contact/active fields | No additional business dependency between non-key contact fields is assumed. |
| Product | ProductID and SKU each determine description, vendor and flags | Vendor details are held separately. |
| ReturnHeader | ReturnID and ExternalReference each determine ReceivedAt and ReceivingUserID | Receipt facts are not repeated on item rows. |
| ReturnItem | (ReturnID, LineNumber) -> all item facts | Product descriptions, location names and reference labels are absent. An open serial uniqueness rule is conditional, not a lifetime candidate key. |
| Inspection | InspectionID -> item key, actor, time, type, grade, result, notes and optional local WorkOrderNumber | The local number alone does not determine the item; composite order FK includes the existing item key. |
| WorkOrder | (ReturnID, LineNumber, WorkOrderNumber) -> Technician, status, times, details and cost totals | No proper subset determines a work order. Item-level facts remain in ReturnItem. No global order ID is stored. |
| InventoryMovement | MovementID -> item, both locations, actor, time, type and notes | Source/destination are event facts, not copies of location names. |
| Location | LocationID and LocationCode each determine name, type and active flag | Type descriptions are in ReferenceValue. |
| VendorClaim | ClaimID and (ReturnID, LineNumber) each determine the remaining claim facts | Both keys enforce the zero-or-one lifetime claim rule; requested/settled values are different facts. |
| SalesSummary | (ProductID, CalendarMonth) -> UnitsSold, source, entering actor and update time | Neither product nor month alone determines a summary. |
| AppUser | UserID and LoginIdentifier each determine DisplayName and IsActive | Role descriptions are absent. |
| Role | RoleID and RoleCode each determine Description and IsActive | Permission meanings are controlled by the implementation. |
| UserRole | (UserID, RoleID) is the full key; no non-key attributes | Resolves M:N without repeating roles in AppUser. |
| AuditLog | AuditID -> actor, time, action, entity, key, old/new documents and transaction ID | The audited record key does not determine all audit events; many events can describe the same business record. |
| ReferenceValue | ReferenceValueID and (Domain, Code) each determine description/active flag | Code alone is not a key across all categories. |

### 3.3 Selected work-order key and 3NF conclusion

Keep **15 tables**. WorkOrder uses the composite primary key `(ReturnID, LineNumber, WorkOrderNumber)`. WorkOrder is a dependent weak entity, identified by its owning item plus the partial key WorkOrderNumber. Each item's first order is number 1; later orders use 2, 3 and so on. The number may repeat on a different item and is never treated as a globally unique identifier. Inspection stores its required item key plus an optional WorkOrderNumber. Its composite foreign key `(ReturnID, LineNumber, WorkOrderNumber)` references WorkOrder's primary key.

For example, item `(1001, 1)` and item `(1001, 2)` can each have order number 1. An inspection for item `(1001, 1)` with WorkOrderNumber 1 identifies `(1001, 1, 1)`. It cannot link to `(1001, 2, 1)`. Initial and unrepaired Final inspections leave WorkOrderNumber NULL; their independent item FK remains mandatory. Repaired PostRepair/Final inspections require the local number and the latest completed order check.

This removes the dependency from a global work-order ID to the item columns in Inspection: the local number alone determines neither ReturnID nor LineNumber. WorkOrder non-key facts depend on its complete three-column key. It stores no item description, reason or current location. Inspection facts depend on InspectionID, and it stores no copied order costs or completion date. These keys and the dependencies in Section 3.2 support a 3NF base design under the stated business assumptions. Review the actual DDL and sample constraints before claiming implementation compliance.

Allocate numbers inside the controlled create-work-order transaction: lock the parent ReturnItem, confirm no active order, read the highest existing number using a current/locking read, allocate the next positive number (1 when none exist), then insert. Do not use AUTO_INCREMENT for a local number. The primary key enforces uniqueness, and the shared item lock prevents two simultaneous allocations. Never reuse or renumber historical work orders. Every client, report, audit record key and future API carries all three key components.

The FRD data requirements, ERD attribute dictionary and editable diagram have been synchronized to this selection. Reporting views remain joined/derived outputs rather than normalized base relations.

## 4. Integrity controls

| Rule | Implementation responsibility |
| --- | --- |
| Unique SKU, external return reference, location code and login | UNIQUE constraints with NOT NULL key columns. |
| One item per positive line number | Composite item PK, positive LineNumber CHECK; intake procedure commits header plus at least one line. A header FK cannot enforce the minimum child count. |
| Required serialized unit; no second open product/serial pair | Store serials normalized as trimmed uppercase text; convert blank optional serials to NULL. Lock Product before checking existing open serials using a locking read. All intake/closure writes follow this product-then-item lock order. |
| Correct active reference category | FK to ReferenceValueID plus controlled lookup of Domain and IsActive. Use a locking read while validating so concurrent reference maintenance cannot invalidate a selection before commit. |
| One active work order | Lock the item, check Open/InProgress orders with a locking/current read, then create/start; no direct staff table writes. Historical Completed/Cancelled rows remain. |
| Same-item, latest completed repair inspection | Composite item/order FK plus locked item/order validation; inspection time at or after completion; reject a different or earlier order. Initial has no order. |
| Numeric/time validity | CHECK for nonnegative costs, positive line number, nonnegative sold units and 0/1 flags. Procedures check status-dependent timestamp/amount requirements and ordered events. |
| Terminal status and outcome | Controlled state transitions; final movement requires matching approval/value, and restock additionally requires latest Pass and grade A/B. CompletionAt set only on terminal disposition. |
| One lifetime vendor claim | Composite UNIQUE(ReturnID, LineNumber) in VendorClaim; reject creation after closure. Settlement is one positive received amount/time in Settled state; other states keep settlement fields NULL. |
| No destructive history deletion | Restrict parent deletes; no cascade deletes through operational/audit history. Deactivate referenced accounts, locations, roles and reference values under FRD guards. |

CHECK constraints handle same-row predicates; cross-table state, roles, category and timing checks belong in controlled transactions. MySQL restricts CHECK expressions, including subqueries. See [MySQL CHECK constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html).

## 5. Roles and authenticated actor

Use a separate limited MySQL login for each fictional staff member during the CLI demo, with a matching unique AppUser.LoginIdentifier. Provision only explicit local accounts; anonymous/proxy identities are excluded from this demonstration. Procedures resolve the connection's session identity to an active AppUser and its active UserRole/Role assignments. They do not accept an arbitrary acting UserID as authorization.

In a definer procedure, CURRENT_USER() identifies the definer, so it must not be used as the business actor. Resolve the connection identity using USER()/SESSION_USER() under the explicit-account convention. Stored routines use a dedicated least-privileged owner, not a student staff account or unrestricted root. Grant callers EXECUTE only on allowed routines; the routine rechecks business permissions. See [MySQL routine security](https://dev.mysql.com/doc/refman/8.4/en/create-procedure.html) and [stored-object access control](https://dev.mysql.com/doc/refman/8.4/en/stored-objects-security.html).

| Capability | Receiving | Inspector | Technician | Manager | Administrator |
| --- | --- | --- | --- | --- | --- |
| Search operational items/history without money | Yes | Yes | Yes | Yes | Requires operational role |
| Intake and permitted movement | Yes | No | No | Requires Receiving role | No |
| Record inspection | No | Yes | No | Requires Inspector role | No |
| Start/complete repair | No | No | Assigned work only | Requires assigned Technician role | No |
| Products/vendors, approvals, assignments, claims, sales | No | No | No | Yes | No |
| Operational reports RQ-01/02/03/05 | Yes | Yes | Yes | Yes | Requires operational role |
| Financial fields and RQ-04 | No | No | No | Yes | Requires Manager role |
| Accounts, membership, roles, locations, reference maintenance | No | No | No | No | Yes, with history/workflow guards |
| Audit review | No | No | No | Authorized business/financial view | Redacted administrative view |
| Direct protected table or audit INSERT/UPDATE/DELETE | No | No | No | No | No |

Permissions combine when a user holds several active roles. No role implies another. An Administrator is trusted to provision approved memberships but does not automatically receive business/financial access; membership changes are audited. Ordinary base-table SELECT is also denied where it would expose financial data. Expose safe operational views and Manager-only report procedures instead. SQL administrators retain operational power outside this business-role model and are not used as staff during access tests.

Do not store database passwords in AppUser or source files. Use client prompts/local credential configuration. Local development is loopback-only; remote deployment requires authenticated encrypted connections. No production deployment or encryption test is claimed here.

## 6. Controlled writes, transactions and audit

Public write procedures own the transaction boundary and are called without an existing caller transaction. Shared internal validation routines do not independently commit. Unexpected SQL errors exit through ROLLBACK followed by RESIGNAL; expected business rejections use SIGNAL with a useful message. Keep DDL/build actions separate from operational transactions.

For writes to existing items, acquire locks in this order where needed: authenticated account/role rows, relevant reference rows, Product, ReturnItem, then its work-order/claim/location rows in stable key order. Every routine uses the same ordering for shared resources. Reference/user deactivation uses matching locking checks and blocks when active work depends on the row. A deadlock or timeout rolls the procedure transaction back; the client can retry the complete operation after re-reading state.

Product locking is a deliberately coarse midterm solution for serial-intake races. It requires no additional reservation table. It trades concurrency within a product for a straightforward, demonstrable rule. Lock the Product before the item when closing serialized items too. Use locking/current reads after waiting, not an older consistent snapshot, for competing state checks. MySQL [locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) require an active transaction to hold these locks.

### 6.1 Movement transaction

1. Resolve the actor and require Receiving access. Start a transaction and create a fresh transaction identifier in trusted code.
2. Lock the relevant product/item and location/reference rows; verify the supplied source equals current location, destination is active/different and item is not terminal.
3. For a final movement, recheck Manager approval, matching path/value and current restock eligibility. A routine relocation preserves status.
4. Insert InventoryMovement. One AFTER INSERT trigger updates ReturnItem.CurrentLocationID. The procedure does not duplicate this location update.
5. Set terminal ItemStatusID/CompletionAt when appropriate. Append the movement audit record and any approval/status/completion audit changes within the same transaction.
6. Commit once; any exception rolls back movement, item and audit together.

The ReturnItem audit trigger captures OLD/NEW values for location and other changed protected fields. Other protected writes use audit triggers or their designated procedure, with one documented owner for each audit event to prevent duplicates. AuditLog has no business-role direct write permission. Derive actor identity from the authenticated connection; if a transaction-label session variable is used, each public routine overwrites it before writing. Such variables never establish authorization. Triggers do not start or commit their own transaction; see [MySQL trigger syntax](https://dev.mysql.com/doc/refman/8.4/en/trigger-syntax.html).

Audit all protected inserts/changes: items, inspections, repairs, movements, approvals, costs, claims, sales and identity/reference administration. OldValues is NULL on insert; NewValues is NULL only for an allowed disposable-record deletion. Do not expose audit JSON containing financial values to non-Managers; use a genuinely redacted view rather than granting AuditLog access and hiding columns in the client. Failed transactions leave no committed business-change audit rows; rejection messages are test evidence, not falsely committed audit events.

### 6.2 Other write boundaries

| Operation family | Main checks and effects |
| --- | --- |
| Receive return | Active inputs; serial rules; header plus all lines; initial status/location; no empty committed header. |
| Record inspection | Inspector; permitted state/type; valid grade/result; required work-order key and timing; append-only inspection; apply the FRD transition. |
| Approve/withdraw disposition | Manager; AwaitingDecision with latest conclusive inspection; restock checks; correct value; audited withdrawal clears approval and cancels only an unstarted order. |
| Assign/start/complete repair | Manager assignment; assigned Technician start/complete; one active order; explicit total cost inputs; Open cancellation only; completion sends item to AwaitingFinalInspection. |
| Claim/sales maintenance | Manager; lifetime claim and status rules; first-of-month sales key; positive settlement; closed item facts unchanged by later settlement. |
| Administration | Administrator; active/history guards; preserve referenced codes/domains; prevent disabling required roles/codes or occupied locations; reassign active work before disabling an account. |

Latest applicable inspection uses InspectedAt and InspectionID as a deterministic tie-breaker. Latest completed order uses CompletedAt and WorkOrderNumber within the item. Event times are assigned/validated by controlled writes, not arbitrary future values. A later Fail/Inconclusive overrides an earlier Pass.

## 7. Reports, views and indexes

Build two joined reporting views initially: `vw_open_items` without financial fields, and Manager-only `vw_item_recovery` at one row per item. These are joined/derived outputs over normalized storage, not extra base tables or materialized totals.

| Report | SQL design |
| --- | --- |
| RQ-01 Open returns | Join header/item/product/location/status; CompletionAt IS NULL; optional status/location filters; oldest ReceivedAt first. |
| RQ-02 Item history | UNION ALL inspection, repair, movement and audit/approval events into an item timeline; consistent event key/time ordering; money only in Manager output. |
| RQ-03 Monthly return rate | Aggregate returned item counts by receipt month and product separately from SalesSummary; combine product/month keys from both sources so missing-sales and zero-return cases are retained; use NULLIF denominator and display NULL as N/A. |
| RQ-04 Recovery value | Pre-aggregate labor/parts by item before joining item/claim. COALESCE non-applicable values to zero; add received settlements only. Filter on item completion period; separate estimate/cash columns. |
| RQ-05 Turnaround/delay | Completed average uses precise elapsed seconds divided by 86400; only completed items. Separate open-item list older than seven elapsed days. |

Use EXPLAIN on representative queries before adding more indexes. Initial candidate indexes supplement PK/UNIQUE/FK-supporting indexes; avoid duplicate indexes with the same usable leading columns.

| Table | Candidate index / purpose |
| --- | --- |
| ReturnHeader | (ReceivedAt, ReturnID): receipt-period joins and ordering. |
| ReturnItem | (ProductID, SerialNumber, CompletionAt): serial/open lookup; (ItemStatusID, CurrentLocationID): filtered open work; (CompletionAt): completed-period selection if useful. |
| Inspection | (ReturnID, LineNumber, InspectedAt, InspectionID): latest item check and history; work-order FK index uses (ReturnID, LineNumber, WorkOrderNumber). |
| WorkOrder | (ReturnID, LineNumber, WorkOrderStatusID): active work; (AssignedTechnicianUserID, WorkOrderStatusID): assigned queue. |
| InventoryMovement | (ReturnID, LineNumber, MovedAt, MovementID): ordered history; source/destination FK indexes. |
| VendorClaim | Unique item pair already supports item claim lookup. |
| SalesSummary | Composite PK already supports product/month retrieval. |
| AuditLog | (EntityName, RecordedAt): history filtering; (TransactionID): transaction evidence. JSON record keys are resolved carefully by the timeline query. |
| UserRole | Composite PK for user's roles; ensure a RoleID-leading index for the Role FK. |

For class-sized data, do not add caches, partitions, replicas or scheduled summary tables. Batch fictional-data loads in bounded transactions, paginate long histories, and stream large extracts. Measure writes/deletes as well as reads because extra indexes increase maintenance cost. Report measured results only after the database runs.
